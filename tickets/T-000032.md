## Goal
Audit and harden the app to guarantee that opening any file (text, binary, hex) never executes, evaluates, or interprets file contents as code or instructions — prevent injection via filenames, metadata, syntax highlighting, export rendering, and format definition parsing

## Acceptance Criteria

### Audit — no eval, no code execution from file contents
- [ ] No use of `NSAppleScript`, `Process`, `NSTask`, `eval`, `JSContext`, `WKWebView.evaluateJavaScript`, or `NSExpression` with user-supplied strings anywhere in the codebase
- [ ] Syntax highlighter (PygmentsSwift) operates purely as a tokenizer — verify it never executes or imports file contents as code
- [ ] Export rendering (PDF/PNG via `DocumentExporter`) uses `NSAttributedString` drawing only — no HTML/CSS rendering of file contents via WebView
- [ ] Format definition expression evaluator (T-000031 `$field_name` offsets) uses a safe arithmetic-only parser — no general-purpose expression evaluation

### Filename / path injection
- [ ] Filenames are never interpolated into shell commands, AppleScript, or URLs without sanitization
- [ ] Window titles, tab titles, and status bar text display filenames as plain text — no attributed string interpretation of filename contents
- [ ] Export dialogs (`NSSavePanel`) use filenames as `nameFieldStringValue` safely (already sandboxed by AppKit)

### File content isolation
- [ ] Opened file data is never passed to `NSAttributedString(html:)`, `NSAttributedString(rtf:)`, or any rich-text decoder that could trigger resource loading
- [ ] Hex view format parsers (`FileLayout`, `FileFormatInterpreter`, `MagicBytes`) only read bytes — no pointer following, no URL fetching, no external resource loading based on file contents
- [ ] SQLite format database (`formats.db` from T-000031) is opened read-only with `SQLITE_OPEN_READONLY` — no triggers, no custom functions, no `load_extension`
- [ ] Search/replace operates on plain string matching — no regex eval of file contents as patterns (user types the pattern, file is the haystack, never reversed)

### Hardening
- [ ] App Sandbox entitlement enabled (com.apple.security.app-sandbox) — restricts file system and network access
- [ ] No outbound network requests triggered by opening a file (AI explain feature in T-000030 requires explicit user action, never automatic)
- [ ] Add a `SECURITY.md` documenting the threat model and these guarantees

## Notes
**Threat model**: A malicious file should never be able to execute code, exfiltrate data, or modify system state simply by being opened in qw. The app is a *viewer/editor*, not an *interpreter*.

**Attack surfaces to audit:**
1. **Text editor** — file contents rendered via `NSTextView` / `UITextView`. These are safe for plain text but verify no rich text mode is accidentally enabled.
2. **Syntax highlighting** — PygmentsSwift tokenizer. Confirm it's pure string parsing, not Pygments-the-Python-process.
3. **Export** — `DocumentExporter` renders to PDF/PNG. Confirm no WebView pipeline.
4. **Hex view** — format parsers read bytes. Confirm no pointer chasing into memory or URL fetching.
5. **Filenames** — displayed in titles, used in save dialogs. Confirm no injection.
6. **Format definitions DB** — SQLite opened read-only. Confirm no triggers/extensions.
7. **CLI tool** — `cli/qw` bash script. Audit for command injection via filenames with special characters (`$()`, backticks, semicolons).

**Grep checklist:**
```bash
# Should return zero results in app code:
grep -r 'NSAppleScript\|Process(\|NSTask\|evaluateJavaScript\|JSContext\|NSExpression' qw/qw/
grep -r 'NSAttributedString.*html\|NSAttributedString.*rtf' qw/qw/
grep -r 'load_extension\|sqlite3_load_extension' qw/qw/
```
