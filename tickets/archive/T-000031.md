## Goal
Replace hardcoded file format parsers with a data-driven system: load magic bytes, section layouts, and field annotations from a bundled SQLite database or JSON/YAML config that can be updated independently of the app binary — like antivirus definition updates

## Acceptance Criteria

### SQLite Definition Database
- [ ] Bundled `formats.db` SQLite file ships with the app (in app bundle Resources)
- [ ] Schema with three tables:
  - `signatures` — magic bytes, offset, mask, file type name, description, icon
  - `sections` — foreign key to signature, section name, offset expression, length expression, kind (header/metadata/data/footer/chunk), color, description
  - `fields` — foreign key to section, field name, offset (relative to section start), size, type (uint8/16/32/64, int, float, double, ascii, bytes, magic), endianness, display format, value mappings (JSON for enum-like values e.g. `{"0":"Grayscale","2":"RGB"}`)
- [ ] Offset/length expressions support: literal integers, references to prior fields (`$field_name`), and simple arithmetic (`$box_size - 8`) for container formats like MP4/PNG chunks
- [ ] Version number in a `metadata` table for update tracking

### Runtime Loader
- [ ] `FormatDatabase` class that opens the SQLite file read-only and provides:
  - `detect(data:) -> FileSignature?` — replaces `MagicBytes.detect()`
  - `sections(for signature:, data:) -> [FileSection]` — replaces `FileLayoutDetector`
  - `fields(for signature:, data:) -> [FieldValue]` — replaces `FileAnnotator`
- [ ] Expression evaluator for offset/length fields that resolves `$references` against already-parsed field values
- [ ] Existing Swift parsers (`PNGLayout`, `ELFInterpreter`, etc.) become the seed data for the initial `formats.db` — all current formats must work identically after migration
- [ ] Falls back gracefully if a format definition has errors (log warning, skip malformed sections/fields)

### Update Mechanism
- [ ] App checks for updated `formats.db` in `~/Library/Application Support/qw/formats.db` — user copy takes precedence over bundled copy
- [ ] Menu item "Hex > Update Format Definitions..." that:
  - Fetches latest `formats.db` from a configurable URL (default: GitHub release asset)
  - Shows version comparison (current vs available)
  - Downloads and replaces the user copy
  - Reloads definitions without app restart
- [ ] `formats.db` is versioned — only updates if remote version > local version
- [ ] Manual import: "Hex > Import Format Definitions..." to load a custom `.db` file

### Developer / Community Workflow
- [ ] CLI tool or script (`tools/format-db-editor.py` or similar) to:
  - Add/edit/remove format definitions in the SQLite database
  - Export the database as human-readable YAML/JSON for review
  - Import from YAML/JSON back to SQLite
  - Validate all definitions (check offset expressions, field types, etc.)
- [ ] README section explaining how to contribute new format definitions
- [ ] Seed database ships with at least: PNG, JPEG, GIF, PDF, ZIP, ELF, Mach-O, MP4, WAV, Gzip, Bzip2, XZ, WASM, PE/EXE, SQLite, XML

## Notes
Think of this like ClamAV signature updates or Wireshark protocol dissectors. The app is the engine; the database is the knowledge. Community can contribute new formats by submitting a PR with YAML definitions that get compiled into `formats.db`.

**Architecture:**
```
formats.db (SQLite, read-only at runtime)
├── signatures    → magic bytes detection
├── sections      → layout / section highlighting
├── fields        → field-level annotation & decoding
└── metadata      → version, last_updated, source_url

Load order:
1. ~/Library/Application Support/qw/formats.db  (user updates)
2. App.bundle/Resources/formats.db              (bundled fallback)
```

**Expression examples for dynamic offsets:**
- PNG chunk: offset = `$prev_chunk_end`, length = `$chunk_length + 12`
- ELF section headers: offset = `$e_shoff`, count = `$e_shnum`, entry size = `$e_shentsize`
- MP4 box: offset = `$prev_box_end`, length = `read_uint32($offset, BE)`
